# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A macOS menu bar app showing live status of every Claude Code chat across repos. Two components connected by JSON files on disk:

1. **`update_status.py`** — a Claude Code hook script. Each lifecycle event (SessionStart, UserPromptSubmit, Stop, …) runs it with a positional arg naming the event; it merges state into `~/.claude/chat-status/<session_id>.json`.
2. **`ChatStatusBar.swift`** — the entire app (single file, AppKit, no Xcode project). Polls that directory every 2s, renders menu bar counts + card dropdown, fires notifications on transitions to *needs you* / *errored* / *finished*.

`install.sh` wires them together by patching hooks into `~/.claude/settings.json` via jq.

## Commands

```bash
./build.sh        # swiftc-compiles ChatStatusBar.swift into build/ChatStatus.app (ad-hoc signed)
./install.sh      # build + register hooks + (re)launch — idempotent
./install.sh --uninstall   # strip hooks + login item
./build/ChatStatus.app/Contents/MacOS/ChatStatus --dump   # print parsed state without the GUI
touch ~/.claude/chat-status/.debug   # log every raw hook payload to ~/.claude/chat-status/_debug.jsonl
CHAT_STATUS_DIR=<dir> CHAT_STATUS_APPEARANCE=light|dark <binary>   # run against other status files (demo screenshots)
```

There are no tests. To verify changes end-to-end: `./install.sh`, then drive a Claude Code session and watch the JSON files / app. `--dump` and `.debug` are the debugging tools.

## Architecture and invariants

**Data flow:** hook event → `update_status.py <arg>` (payload on stdin) → status JSON file → app poll. The contract between the two sides is the JSON schema (`status`, `waiting_on`, `waiting_kind`, `waiting_rich`, `error_type`, `fail_streak`, `turn_started_at`, `updated_at`, `repo`/`branch`/`cwd`, `title`, `last_prompt`, `pid`/`pid_started_at`, `background`, `last_message`, `host`/`host_app`/`host_pid`, `bb_thread`, `bb_title`, `agent`, `repos_touched`/`repo_hits`/`repos_stale`) and the status vocabulary: `live`, `working`, `needs_input`, `error`, `done`. Changing either side means changing both — plus `install.sh`, whose event→arg mapping must match the dispatch in `update_status.py`'s `main()`.

**Codex shares the hook.** `install.sh` also patches `~/.codex/hooks.json` (when `~/.codex` exists) to run `update_status.py <arg> codex`. Codex payloads use Claude's field names, so the dispatch is shared; the second argument sets `agent: "codex"` on the entry and makes the ancestor walk look for a `codex` process. Codex events: SessionStart, UserPromptSubmit, PostToolUse, PermissionRequest, Stop, SessionEnd, plus Interrupt → `interrupt` (back to `live`). It has no Notification / StopFailure / PostToolUseFailure. Codex skips hooks the user has not trusted (`/hooks`), and under `codex app-server` (VS Code extension, bb) one long-lived process serves every thread, so PID reaping rarely fires for Codex cards and bb's `BB_THREAD_ID` is absent; for those the hook reads `bb_thread` from bb's database instead (`bb_thread_for`: `~/.bb/bb.db`, `events.provider_thread_id` = Codex session id → `thread_id`, read-only, retried each event until found). The app tags these cards "Codex" (`Chat.hostTag`) and never sends a Codex session id to the Claude Code deep link.

**`update_status.py` must never print to stdout.** Hook stdout is interpreted by Claude Code — PermissionRequest output can auto-approve/deny, PreToolUse output can rewrite tool calls. It must also always exit 0 (never block Claude), which is why everything is wrapped in bare try/except.

**State semantics encoded across both files:**
- Only `UserPromptSubmit` creates a status file. Every other event returns early when the session has no file, so opening or restoring a chat tab never makes a card, and a manually removed card stays gone until the next prompt.
- `repo`/`branch`/`cwd` are pinned on the session's first write and never overwritten — the card stays attached to the window it opened in even if the chat `cd`s elsewhere. Click routing depends on `host` (the session's topmost ancestor app, detected in the hook's process walk and re-pinned with the PID): `vscode` (or missing, for pre-host files) opens `cwd` in VS Code then deep-links `vscode://anthropic.claude-code/open?session=…`; `terminal` just activates the host app via `host_pid` (no deep link, no tab-level focus — and a tmux server isn't a GUI app to activate). A chat run by bb also carries `bb_thread` (from the `BB_THREAD_ID` env var bb gives its agents); a click runs `~/.bb/bin/bb thread open <id>` first, so bb shows that thread.
- `repos_touched` lists the repos the chat's tool calls worked in, most evidence first (max 6), so a chat pinned to a workspace folder of many repos can say where it really is. `touched_repos()` reads file-tool paths and, for shell commands, every word that is an existing path plus the command's `cwd`; `repo_of()` resolves each by a stat-only walk up to a `.git` (a linked worktree is named after its main repo). It is updated on tool / toolfail / permission events. Every repo seen goes into `repo_hits` (`[[name, evidence], …]`, hook-internal): a read or shell mention adds 1, an edit adds `REPO_SHOWN_AT` (2), and only repos at or above that reach `repos_touched` (most evidence first), so one stray `ls` of a neighbour does not relabel the card. A new prompt sets `repos_stale` instead of clearing either list, and the next touch starts them over, so the list always covers the latest turn that touched anything. The app shows `Chat.project` (first touched repo, else `repo`) and colors by it; routing still uses the pinned `cwd`.
- `bb_title` is bb's own title for the thread, re-read from `~/.bb/bb.db` (`threads.title`, read-only) on every event while `bb_thread` is set, because bb writes it shortly after the first prompt and can change it. Titles still carrying bb mention tokens (`@thread:` …) are skipped. `summaryText(for:)` returns it ahead of the on-device summary, and `ensureSummary` skips those chats; a user label still wins.
- `turn_started_at` is stamped only by UserPromptSubmit; tool events refresh `updated_at` but not the turn clock. The app ages *working* cards from `turn_started_at` and everything else from `updated_at` (see `Chat.activityDate`).
- `waiting_rich` marks precise blocked-on text (from PermissionRequest / AskUserQuestion) so the generic Notification message that follows doesn't clobber it.
- Status writes are atomic via a PID-unique tmp file + `os.replace` — hooks fire concurrently for one session.
- `error` comes from StopFailure because `Stop` never fires on API errors; without it a dead turn looks *working* forever.
- `pid`/`pid_started_at` (the Claude process, found by walking the hook's ancestors; re-pinned on SessionStart and each prompt) let the app reap sessions that died without a SessionEnd. The start time defends against PID reuse; the ancestor walk must skip the hook's own chain, whose command line contains "claude" via the repo path.
- A `Stop` with any `background_tasks`/`session_crons` entry `status == "running"` is not *done*: the entry stays `working` with `background: true` (no finished ping), and `idle_prompt` notifications are ignored while it's set. `last_message` (Claude's closing message, payload field or transcript tail-parse) is only written on a true finish.
- Notifications are keyed `chat-<session_id>` — one live banner per chat; `poll()` withdraws delivered banners when a chat returns to `working`/`live` or its file disappears.

**Swift file layout** (top to bottom): `Chat` struct + file loading/pruning → `FMEngine` (Apple on-device Foundation Models, macOS 26+, availability-gated so its types never leak elsewhere) → `Palette` (fixed "flourish" signal colors) + `Theme` (the neutral black/white scheme, chosen per light/dark from `panel.effectiveAppearance`; only Palette's status hues stay constant) + `PixelMark` (the 8-bit panes/sunburst mark, drawn procedurally on integer grids; also the menu-bar template glyph) → `ProjectStyle` (a stable color per repo: slots handed out so repos on screen together differ, persisted as `projectColors`, skipped under `CHAT_STATUS_DIR`) + `SourceIcon` (host app and Codex as app icons, text only when a host has no icon; a Claude chat run by bb gets a drawn clay spark, since bb runs both agents) → `Spark` (fixed-size cached frames of the CLI's thinking glyphs, tinted clay — the animated working indicator in the bar and on rows) → `Toggle` (custom monochrome pill switch) → `ChatCardView` (dropdown-row rendering + inline rename + drag-to-reorder) → `GalleryTileView` → `AppDelegate` (status item, panel, polling, notifications, Carbon global hotkey ⌃⌥C). Persistent app state (AI-summary cache, user labels, manual card order, toggles, hotkey binding) lives in `UserDefaults` under `com.measure.chatstatus`. **Card order has two modes** behind the `manualOrder` pref, surfaced as the "Auto order" OPTIONS switch (on = automatic; shown inverted since the pref stores *manual*) plus a right-click item, defaulting to *automatic* — the status sort `loadChats()` applies (needs_input first). In *manual* mode `sortedChats()` runs `ordered()` instead: dragging a card writes `cardOrder` (a list of session ids), which `ordered()` reconciles on every load — dead sessions pruned, new sessions prepended by recency. Switching into manual seeds `cardOrder` from the current view the first time so nothing jumps, and keeps any prior arrangement after that. Dragging is gated by `ChatCardView.reorderable` (true only in manual mode); a drag is told from a click by a 4 pt threshold and forwarded up to the `AppDelegate`, since a reorder spans the whole hand-laid card stack; `poll()` skips its panel rebuild while `isReordering`. The panes/sunburst pixel geometry is duplicated in `make-icon.swift` (which renders the "4e Cream" app icon) since it compiles as a separate unit — keep the two cell definitions in step.

**Pop-out gallery:** a second, floating `NSPanel` (`AppDelegate.gallery`) showing one square `GalleryTileView` per chat in the dropdown's order (click routes, hover ✕ removes the status file; rename/reorder stay in the dropdown). It is independent of the dropdown: rebuilt by `syncGallery()` only when `galleryPrint()` changes (never on a timer, so hover survives), animated from the same `animTick`, toggled by hotkey id 2 (⌃⌥⇧C) on the shared Carbon handler. `galleryOpen` and `galleryTopLeft` persist in `UserDefaults`; the window is anchored by its top-left corner so it grows down/right as chats come and go. Tiles override `hitTest` to claim clicks, because the window drags by its background. Tiles are quiet rounded cards whose status shows as a `CAGradientLayer` wash of the status hue (plus a hue edge for needs-you / error); they reuse `Spark` and the rows' glyph vocabulary. A tile for a bb chat (`bbThread` set) in *needs_input* with `waitingKind == "permission"` also shows Deny / Allow pills at its foot on hover (hit-tested in `mouseUp` like the ✕). They call `BBInteraction.answer`, which runs `bb thread interactions list|approve|grant|deny` off the main thread; when bb has no pending approval the tile falls back to its normal click.

**bb plugin:** `bb-plugin-chat-status/` is a separate TypeScript package (a bb plugin, built by `bb plugin build`, not by `build.sh`). `server.ts` reads the same status files and the app's `projectColors` / `labels` preferences read-only; `app.tsx` replaces bb's thread list (`experimental_threadList`, exclusive: one plugin owns it) with *Today* (a card per thread that ran since local midnight, is busy or waiting, or is pinned; the rest under a collapsed *Earlier*; membership is derived on each render, never stored) and draws a sidebar-footer list of chats outside bb. Replacing the list means the plugin draws every row itself: bb's context menu, status glyph and provider icon come from SDK components, but bb's drag-to-reorder, sections and sub-thread nesting are not reimplemented (sub-threads are flat cards). Cards tag repos by short name: `shortRepo()` drops a `measure-` prefix, and `REPO_SHORT` holds the names that rule gets wrong (`contributor`, `msr-web`, …); colors still key on the full name. The pop-out tiles use the same names through a Swift copy (`Chat.shortRepo` / `Chat.repoShort`); keep the two tables in step. `repos.ts` is a TypeScript port of the hook's `touched_repos` / `repo_of` over bb's stored tool calls (`threads.events.list`, `item/started`), so bb rows name repos for every thread, not only hooked ones; keep its rules in step with the hook's. `feed.ts` is a second writer of status files: it turns bb's thread events (`thread.active` / `idle` / `failed`, `interaction.pending`) into `bb-<threadId>.json` for threads no hook file covers (matched by `bb_thread`), and for hook-covered threads only flips a still-`working` file to `needs_input` (a question or form, marked `feed_waiting`) or `error` after a 3 s grace so the hook writes first. It consumes the JSON contract, so a schema change means changing it too, and its `PROJECT_HUES` / `STATUS_HUE` are copies of `ProjectStyle.hues` / `Palette`. **For me** (the private work tracker in the separate `measureprotocol/worklog` repo): the `worklog` CLI is the whole contract. `server.ts` runs only `worklog board --json` (to-dos, counts, questions, proposals, `today_thread`, `collector_thread`, `hub_url`) and `worklog hub ensure` (starts the hub web page if it isn't serving and returns its address) and never touches the tracker's files, so worklog can change its storage, port or layout freely. The card refreshes once a minute and whenever a bb thread moves. `app.tsx` puts a `ForMeCard` on top of the thread list: today's For me thread drawn as the clay pixel robot (`Buddy`; moods `sleep` / `work` = collector thread busy / `brief` = today's thread unread / `ask` = to-confirm items or proposals, with a badge), one status line, click opens that thread (or the hub when there is none yet); its "Hub →" link opens the hub. The thread itself is left out of Today so it isn't listed twice. Everything degrades to nothing when the CLI is absent. Today cards come in three tiers, by shape before colour: needs-you / error get a tinted edge and fill, an in-flight card a plain border, and a finished or idle card none (its 1px border is transparent, so nothing shifts).

**Two clocks, not one:** the 2s poll reads state; a separate ~7fps animation timer advances the spark and the per-second turn clocks on working cards. It runs only while a foreground turn is working (`ensureAnimTimer`), so the app never wakes for animation when idle. Card updates from `animTick` mutate labels/images in place — a full `refreshPanel()` mid-animation would reset hover and inline-rename state.

**Do not change the bundle identifier** `com.measure.chatstatus` — the previous id has poisoned status-item state in the window server (see comment in `build.sh`).

**Hooks in settings.json are guarded** by a file-existence check on the script path, so a moved/deleted clone no-ops instead of breaking Claude; `install.sh` strips any prior chat-status hooks before adding, so re-running never duplicates.
